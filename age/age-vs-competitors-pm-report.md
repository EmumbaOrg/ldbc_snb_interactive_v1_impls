**Author:** AGE benchmark team

## TL;DR — Talking points for the meeting

> Use these bullets for the discussion. Each one expands into a numbered
> section below if she pushes for detail.

- **The benchmark target itself is Cypher (Neo4j).** LDBC's official
  validation oracle is generated by the Neo4j/Cypher implementation
  (`age/README.md:305`). Every other engine — including AGE — is being
  measured against output produced by Neo4j. Any semantic gap costs us
  correctness, not just speed.

- **AGE 1.6 is missing core Cypher features that Neo4j, TigerGraph, and
  DuckDB-PGQ all support.** Two LDBC queries (IC13 SingleShortestPath,
  IC14 AllShortestPaths) are **structurally impossible** to express
  in AGE 1.6 — we ship sentinel stubs that always return `-1` / `[]`
  and disable the queries in benchmark runs (`age/README.md:15`,
  `age/queries/AGE-QUIRKS.md:28`). That is a 2-out-of-14 IC gap on day one.

- **Apache AGE 1.6 has a known multi-threaded MVCC bug** (upstream issue
  apache/age#1954). Concurrent inserts crash with `vertex assigned to
  variable X was deleted` — historically aborted the SF3 benchmark
  around op ~2,800 (`age/AGE-1.6-MVCC-BUG.md:46`). Our workaround
  silently drops a small percentage of update ops so the workload
  completes; this is a correctness-cost-for-throughput trade Neo4j
  doesn't have to make. Upstream fix is in AGE 1.7.0 — pending upgrade.

- **AGE has no native datetime, no shortestPath, no multi-label MATCH,
  no pattern-predicate negation with typed relationships, no FOREACH,
  no `CALL { ... }` subquery.** Each missing feature forces us to
  emulate it with hybrid Cypher+SQL, denormalized side tables, or
  `UNION ALL` rewrites that the reference Cypher / DuckDB / TigerGraph
  impls do not need. See `age/queries/AGE-QUIRKS.md` quirks §1–§15 for
  the catalog.

- **AGE's planner mis-estimates cardinalities and falls into pathological
  plans at SF3 and beyond.** Concrete cases we hit and documented:
  - Undirected `-[:KNOWS]-` does a full edge-table scan instead of a
    seed-node index probe → **4–5 seconds at SF3** vs ~50 ms when we
    rewrite to directed (`age/queries/AGE-QUIRKS.md:158`).
  - Single-node MATCH with a parameter compiles to **Seq Scan on a
    6.4M-row Comment table** (4,737 ms / call) because GIN cost
    estimation can't see through the parameter wrapper
    (`age/queries/AGE-QUIRKS.md:254`, `age/optimization-plan-2026-05-15.md:353`).
  - IC5's per-(Person, Forum) post count compiles to a parallel hash
    join over the full Post + HAS_CREATOR + CONTAINER_OF cross-product
    — **33 seconds mean at SF3** before we denormalised it away
    (`age/results/sf3-final-report.md:67`).
  - IC12 cannot push `WHERE tag.id IN <list>` past a Cypher aggregate
    output, so AGE materialises a 743 K-row pipeline and post-filters
    99.97 % of rows out — Person/broad tagclass takes **51 seconds at
    SF3** and projects to **~85 hours at SF1000**
    (`age/ic12-optimization-bottlenecks.md:389`).

- **`cypher()` call overhead is a flat ~15–150 ms tax** on every query,
  regardless of the actual SQL work. For sub-millisecond short reads
  (SQ1/SQ3/SQ5) this is the dominant cost
  (`age/results/sf3-final-report.md:271`,
  `age/results/optimization-report-2026-05-10.md:323`). Neo4j and
  TigerGraph have no equivalent per-call ceremony.

- **Where AGE is "competitive" is the result of hybrid SQL workarounds,
  not native graph performance.** Our throughput trajectory at SF3
  went from 3.30 ops/s (Cypher-heavy) → 25.08 ops/s (iter-3: SQL
  recursive CTEs replace Cypher BFS for IC1 / IC5) — **7.6× by moving
  work out of AGE Cypher into outer SQL**
  (`age/results/sf3-denorm-iter3-report.md:30`). That's a tell: the
  graph engine is the bottleneck, the relational engine underneath it
  is not.

- **Hardware/config bottlenecks (Docker `/dev/shm` 64 MB default,
  `jit=on` default) further depress AGE numbers** unless deliberately
  tuned. Our 50 % throughput improvement on AGE 1.6 / PG17 came
  partly from `--shm-size=2g` and `jit=off`
  (`age/results/age16-sf3-benchmark-report.md:169`,
  `age/horizon-tuning.md:39`). Reference impls don't need these knobs.

- **Bottom line for the PM:** AGE's gap is not a "tune the queries
  better" problem. It is a feature, planner, and runtime-overhead gap
  versus mature graph engines. Concrete unblockers — AGE 1.7 upgrade,
  Horizon DB-class hardware, and the schema denorm strategy already
  in flight — close most of it, but several gaps (no shortestPath in
  1.6, no FOREACH, planner-can't-bind-GIN-on-parameter) remain
  structural to the engine.

## 1. Benchmark methodology and the "comparison baseline" question

LDBC SNB Interactive v1 ships with a Cypher reference implementation
(`cypher/` in this repo) which is the **authoritative oracle**: it
generates the validation params and the expected results that every
other implementation is checked against
(`age/README.md:303-305`). That has two implications:

1. The "comparison" is not symmetric. We are not measuring AGE versus
   Neo4j on identical SQL — we are measuring AGE's ability to **match
   Neo4j's output byte-for-byte** while running an equivalent
   Cypher-on-Postgres workload.

2. Any semantic gap in AGE Cypher relative to Neo4j Cypher shows up as
   *correctness failures*, not just *slower runs*. IC13 and IC14 are
   the visible examples: AGE 1.6 has no `shortestPath()` /
   `allShortestPaths()`, so we ship Java handlers that return the LDBC
   "no path" sentinel `-1` / `[]` and disable the queries in
   `driver/validate.properties`. The validator counts every IC13/IC14
   row as Incorrect against any non-trivial param — about ~40 % of the
   visible failure rate on a full validation slice
   (`age/results/sf3-final-report.md:51-55`).

The "other implementations" being referenced in the rest of this
report:

| Impl | Directory | Storage model | Query language |
|---|---|---|---|
| Cypher / Neo4j | `cypher/` | Native graph | Cypher (oracle) |
| TigerGraph | `tigergraph/` | Native graph | GSQL with accumulators |
| DuckDB | `duckdb/` | Columnar relational | SQL |
| Umbra | `umbra/` | Relational | SQL |
| Postgres | `postgres/` | Row-store relational | SQL |
| **AGE** | `age/` | **agtype (JSON-like) on PG row-store with GIN** | Cypher → SQL via `cypher()` macro |

AGE's storage model is the structural disadvantage that propagates
through everything below: properties live as `agtype` (a JSON
super-set) inside a generic `properties` column, with GIN containment
as the only fast access path. The relational impls and Neo4j both
have schema-aware columnar / native-pointer access; AGE doesn't.

## 2. Shortcomings of Apache AGE 1.6 (with file citations)

This section is the catalog. Each item is something that costs us
performance or correctness *relative to* what Neo4j / TigerGraph /
DuckDB get for free. The numbered items mirror
`age/queries/AGE-QUIRKS.md` so engineering can cross-reference.

### 2.1 Missing Cypher language features

| # | Missing in AGE 1.6 | Neo4j? | TigerGraph? | DuckDB-PGQ? | Source |
|---|---|---|---|---|---|
| 1 | `datetime()`, `EXTRACT`, date arithmetic | Yes | Yes | Yes | `AGE-QUIRKS.md:14` |
| 2 | `shortestPath()` / `allShortestPaths()` | Yes | Yes | Yes (recursive) | `AGE-QUIRKS.md:28` |
| 3 | Multi-label MATCH `(:A|B)` | Yes | n/a | Yes | `AGE-QUIRKS.md:40` |
| 4 | Predicate pushdown into `[:REL*1..k]` | Yes | Yes | Yes | `AGE-QUIRKS.md:56` |
| 5 | `ORDER BY` on `RETURN` aliases | Yes | Yes | n/a | `AGE-QUIRKS.md:77` |
| 6 | `UNION` over node objects (returns vertex) | Yes | n/a | n/a | `AGE-QUIRKS.md:88` |
| 10 | `NOT (p)-[:TYPED_REL]-(n)` parser-accepted | Yes | Yes | Yes | `AGE-QUIRKS.md:137` |
| — | `FOREACH` (needed to fold multi-step IUs) | Yes | n/a | n/a | `optimization-plan-2026-05-15.md:142` |
| — | `CALL { ... }` subquery | Yes | n/a | n/a | `optimization-report-2026-05-10.md:230` |

Each row above forces a workaround. Concrete cost examples:

- **No datetime → IC10 birthday-window query.** We precompute
  `Person.birthMonth` and `Person.birthDay` as integer properties at
  load time so we can filter on them; the reference Neo4j query does
  this with `datetime()` arithmetic at query time
  (`AGE-QUIRKS.md:19`).
- **No `shortestPath` → IC13 / IC14 are stubs.** Always counted as
  Incorrect against non-trivial validation params
  (`age/README.md:15`).
- **No multi-label MATCH → every "Message" query becomes `UNION ALL` of
  Comment + Post arms.** Affects IC2, IC3, IC5, IC6, IC7, IC8, IC9,
  IC11, IS2, IS4, IS5, IS6, IS7 — the majority of the workload
  (`AGE-QUIRKS.md:405`).
- **No predicate pushdown into VLE → IC1 unrolled manually to
  3 separate cypher() calls** (`AGE-QUIRKS.md:73`).
- **No `NOT (p)-[:KNOWS]-(n)` → "exclude direct friends from FOF"
  rewritten as `OPTIONAL MATCH` + null check, which in turn measured
  4,900 ms full-table KNOWS scan at SF3** — eventually fixed by
  going to a UNION-deduplicate pattern (`AGE-QUIRKS.md:137-146`).

### 2.2 Storage / type-system shortcomings

- **agtype is type-strict, but loads naturally produce strings.** The
  default agefreighter loader stores every property — including `id`,
  `creationDate`, `joinDate` — as quoted strings. Cypher queries use
  integer literals (`{id: 933}`). `933 ≠ "933"` in agtype containment,
  so **every MATCH returns zero rows** until we patched the loader
  (`age/README.md:130-140`, `AGE-QUIRKS.md:98`). This is a foot-gun
  with no analog in Neo4j / TG / DuckDB.

- **Property MATCH requires GIN; B-tree on extracted values is ignored
  by the planner** (`AGE-QUIRKS.md:106`). Functional B-tree indexes
  on `(id)` extracted from `properties` are not consulted for the
  containment path; we need a GIN index per label *and* the functional
  B-tree for ORDER-BY paths.

- **agtype rebuilds the full vertex blob for every GROUP BY / count
  comparison.** Even after `WITH friend.id AS personId` projection, the
  AGE SQL compiler emits
  `agtype_access_operator(VARIADIC ARRAY[_agtype_build_vertex(friend.id, …, friend.properties), '"id"'::agtype])`
  for the GROUP KEY — i.e. it reconstructs the whole vertex (~300
  bytes) on every comparison. Measured GROUP-by cost on 482 K rows
  ≈ 18.5 seconds **purely in agtype comparison**, not I/O — quicksort
  in-memory was the same cost as external merge sort
  (`ic12-optimization-bottlenecks.md:621-645`).

### 2.3 Planner pathologies (measured, not theoretical)

These are all cases where the AGE / PostgreSQL planner picks a
catastrophically wrong plan and we either reroute around it or live
with the cost. Numbers are from SF3 (24 K Persons, 6.4 M Comments,
2.6 M Posts, 1.13 M KNOWS, 11 GB DB —
`age/results/sf3-final-report.md:5`).

| Pathology | Cost | Repro / source |
|---|---|---|
| Undirected `-[:KNOWS]-` falls back to full edge scan | 4–5 s vs 50–130 ms directed | `AGE-QUIRKS.md:152-174`; IC5/IC9 fix gave 87× speedup |
| Multi-hop OPTIONAL MATCH builds 143 K-row hash that spills 87 MB to temp | +230 ms per hop | `AGE-QUIRKS.md:178-208` (IC1 SF10 EXPLAIN) |
| Parameterised single-node MATCH → cached generic plan locks in Seq Scan | SQ4 4,737 ms vs 5 ms | `AGE-QUIRKS.md:254`, `optimization-plan-2026-05-15.md:353-369` |
| `WHERE id IN <agg-output>` cannot be pushed past Cypher aggregate boundary | IC12 743 K-row Hash Join, 99.97 % rows discarded | `ic12-optimization-bottlenecks.md:407-425` |
| OPTIONAL MATCH `(forum)-[:CONTAINER_OF]->(post)-[:HAS_CREATOR]->(friend)` → parallel hash on full Post × HAS_CREATOR × CONTAINER_OF | IC5 33,350 ms mean at SF3 | `sf3-final-report.md:67` |
| Threshold-flip: NL via index at SF0.1 → hash/merge over full IS_LOCATED_IN at SF3 once friend set crosses ~300 | IC10 V3 stuck > 1 h in benchmark | `sf3-final-report.md:60`, `:115-122` |
| Parallel Seq Scan on Person ignoring `idx_person_graphid` at SF10 (50.8 M rows filtered out) | IC12 BasketballPlayer 4.6 s → 11.8 s | `ic12-optimization-bottlenecks.md:570-580` |

The pattern across all of these: the planner's cost estimates are
formed against the SQL-side row counts and statistics, not against the
graph-traversal semantics, and the agtype wrapping layer hides the
shape of the data from the planner. Neo4j's Cypher cost model is
graph-aware; AGE's is PostgreSQL's relational model squinting through
agtype.

### 2.4 Concurrency / runtime bugs

- **MVCC visibility race on multi-row CREATE inside a transaction**
  (`AGE-1.6-MVCC-BUG.md`). Apache AGE issue #1954, fixed upstream in
  AGE 1.7.0 (PR #2343). Triggers under multi-threaded update workloads
  (IU1 / IU6 / IU7 most affected). Pre-mitigation: SF3 benchmark
  crashed around op ~2,800 at thread_count=4. Post-mitigation: a JDBC
  retry+skip workaround in
  `age/src/main/java/.../AgeUpdateOperationHandler.java` lets the
  workload complete but **silently drops a small percentage of update
  ops** and logs them to `/tmp/age-mvcc-skips.log`
  (`AGE-1.6-MVCC-BUG.md:80-108`).

- **`countCypherCalls()` substring-scans SQL comments.** If a query
  file has the literal token `cypher(` inside a comment, the JDBC
  handler over-counts placeholders and crashes with `column index
  out of range`. Cost us 142 crashes over 2,837 ops in one Phase 3
  measurement (`optimization-plan-2026-05-15.md:339-351`).

- **Variable-length path expansion resolves label name as a
  PostgreSQL composite row type** — so `(tc)<-[:IS_SUBCLASS_OF*1..]-(sub:TagClass)`
  fails with `Invalid number of attributes for ldbc_snb.Person` after
  `denormalize-schema.sql` adds a column to Person. AGE doesn't refresh
  composite-type definitions on schema change
  (`ic12-optimization-bottlenecks.md:330-340`).

- **JIT compilation is net-negative for AGE Cypher.** Measured across
  all 12 IC queries at SF3: biggest win IC6 +11 %, biggest losses IC3
  -13 %, IC12 -11 %, IC7 -7 % (`optimization-plan-2026-05-15.md:205-219`).
  Root cause: AGE's hot path is opaque C functions (`agtype_access_operator`,
  GIN containment) that JIT can't inline. We run with `jit=off` and
  document it as required (`age/horizon-tuning.md:103-105`).

### 2.5 Per-call overhead

Every `cypher()` macro call has a flat **~15–150 ms** ceremony cost —
parser cache miss, agtype boxing on return, JDBC text-mode fetch
(`sf3-final-report.md:271-275`). For complex queries this is in the
noise; for short reads it dominates.

- IS5 (`ShortQuery5MessageCreator`) at SF3 was 3,700 ms mean *before*
  the parameterised rewrite. After: 89 ms. **Of the original 3,700 ms,
  the bulk was AGE per-call ceremony, not query work**
  (`age16-sf3-benchmark-report.md:128-130`). Neo4j answers the same
  query in <1 ms.

- The Phase 3 parameterisation reversal (forced literal substitution
  to bypass GIN parameter-bind bug, §2.3) eliminated the agtype access
  wrapper and lifted SQ4 from 4,935 ms to 65 ms — a **99 % reduction**
  attributable purely to AGE call-path overhead, not the query
  (`optimization-plan-2026-05-15.md:426`).

## 3. Comparative benchmark context

This section sets the AGE numbers against what we know about the
reference implementations. Where we don't have head-to-head numbers
on identical hardware, we say so — these are not claims about
absolute ranking.

### 3.1 SF3 throughput trajectory on AGE (this work)

From `age/results/sf3-final-report.md`,
`age/results/sf3-denorm-iter3-report.md:23-30`,
`age/results/age16-sf3-benchmark-report.md:8-13`:

| Configuration | Throughput | Notes |
|---|---|---|
| SF3 baseline (no fixes) | 3.58 ops/s | Crashes mid-run |
| SF3 after IC10 + IC1 + SQ2 fixes | 5.01 ops/s | Pure Cypher form |
| SF3 iter-2 (aggregate side tables) | 11.78 ops/s | Hybrid Cypher + SQL |
| SF3 iter-3 (SQL recursive CTE for IC1 / IC5 BFS) | **25.08 ops/s** | Hybrid, work moved out of Cypher |
| SF3 AGE 1.6 / PG17 (post-IS5 fix) | 7.92 ops/s | Different env, IS4 still slow |
| SF3 AGE 1.7 / PG18 baseline (other team) | 5.28 ops/s | Reference for comparison |
| SF3 Phase 3 (parameterised path reversal) | **13.5 ops/s** | After empty `age_parameterized_queries` |

The 7.6× headline improvement (3.30 → 25.08 ops/s) is real and
useful, but it came from moving graph work out of AGE Cypher and
into outer SQL recursive CTEs — i.e. by **avoiding the graph
engine**. That is what the iter-3 report admits explicitly
(`sf3-denorm-iter3-report.md:269-275`).

### 3.2 What the reference impls do differently

From cross-references in our reports:

- **TigerGraph** uses per-vertex accumulators (`@distance`) and
  `BREAK` early-termination during BFS expansion
  (`sf3-denorm-iter3-report.md:180-195`). PostgreSQL recursive CTEs
  approximate this but **cannot do early termination** — they always
  expand to the depth bound. For IC1 with very common firstNames at
  SF1000, this is the residual gap.

- **DuckDB / Postgres / Umbra** use schema-native columnar / row
  storage with proper SQL JOINs. They don't pay agtype boxing on
  every value comparison and the planner has full visibility into
  column statistics. The "match postgres single-INSERT IUs"
  hypothesis was tested and falsified for AGE: removing our denorm
  side tables would not let AGE match Postgres throughput, because
  **agtype + GIN makes per-call aggregates slow** in a way that
  Postgres' tabular storage doesn't experience
  (`optimization-plan-2026-05-15.md:131-138`).

- **Neo4j (Cypher reference)** has a graph-aware cost model, native
  shortestPath, multi-label MATCH, full Cypher 5 semantics. Every
  query we work around in AGE compiles cleanly there.

### 3.3 SF1000 projection

After iter-3 (`sf3-denorm-iter3-report.md:160-173`) our SF1000 outlook
for the 12 IC queries is:

| Risk tier | Queries | Reason |
|---|---|---|
| OK at SF1000 with current work | IC1, IC2, IC3, IC4, IC5, IC7, IC8, IC9, IC10, IC11, all SQ, all IU | Hybrid SQL workarounds cover the cost |
| At risk | IC12 | TagClass-tree expansion, projected 76 min – 85 hr by tagclass breadth (`ic12-optimization-bottlenecks.md:395`) |
| Blocked | IC13, IC14 | AGE 1.6 has no shortestPath; AGE 1.7 has it |
| Multi-thread sustained ops | All IUs | Need AGE 1.7 to remove the MVCC give-up rate |

For comparison, the reference Neo4j / TigerGraph impls publish
sub-second p99s on most of these at SF1000 in LDBC's official
result sets. We do not yet have a clean SF1000 number for AGE
on equivalent hardware.

## 4. What's actually fixable, ranked

For the PM conversation, the engineering levers are:

### 4.1 Upgrade to AGE 1.7.0 — biggest single unblocker

- Resolves the MVCC race (no more retry workaround,
  no more dropped IUs) (`AGE-1.6-MVCC-BUG.md:128-138`).
- Ships `shortestPath()` / `allShortestPaths()` — IC13 / IC14 become
  real implementations instead of sentinel stubs.
- Some planner improvements in VLE and OPTIONAL MATCH (yet to be
  measured on our workload).
- **Cost:** Cypher syntax compatibility check, re-validate at SF0.1
  and SF3, remove the retry workaround. Tracked separately.

### 4.2 Move to Horizon DB-class hardware

The 32 vCPU / 256 GB Horizon profile in `age/horizon-tuning.md` lifts
several local-dev ceilings:

- 64 GB `shared_buffers` (vs 4 GB locally) holds SF1000 working set.
- NVMe-tuned `random_page_cost=1.1` and
  `effective_io_concurrency=300` (vs default 1) fix planner Seq-Scan
  bias and give 2–3× bitmap-scan throughput.
- `--shm-size=8g` (vs 64 MB Docker default) eliminates the parallel
  hash join `No space left on device` crashes
  (`age16-sf3-benchmark-report.md:169`).
- Per the Horizon DB note in our memory: schema changes and writes
  there are shared infrastructure, EXPLAINs are run by the user
  themselves; benchmarks on Horizon need coordination.

### 4.3 Continue the schema denorm strategy

The side-table approach (`PersonPostCount`, `ForumMemberPostCount`,
`MessageByCreator`, `Comment.creator_id`, `TagClass.subclass_of_id`)
is what bought the 3.30 → 25.08 ops/s trajectory. It is **not**
anti-pattern: removing `PersonPostCount` was measured as a **7×
regression** on IC10 reads
(`optimization-plan-2026-05-15.md:131-138`). Future denorms
already scoped:
- Tier-1: `HAS_CREATOR.creationDate` denorm + composite index
  (unblocks IC2, IC8).
- Tier-1: TagClass transitive closure (unblocks IC12 at SF1000).
- These are linear engineering work, no AGE engine dependency.

### 4.4 What we cannot fix from outside AGE

- **Per-`cypher()`-call ceremony** (~15–150 ms). This is in AGE's
  parser / agtype-marshalling / JDBC text-mode return path. Either
  AGE upstream optimises it or we live with it. Affects every query.
- **Planner cardinality estimation through agtype.** The planner
  cannot see column statistics for `properties @> agtype` predicates,
  cannot push filters through Cypher aggregate boundaries, and
  cannot bind GIN cost estimates on parameter values. Each of these
  is an upstream engine improvement, not a query-author lever.
- **`FOREACH`, `CALL { ... }` subquery, multi-label MATCH** — Cypher
  language features missing from AGE 1.6; we cannot add them
  ourselves.

## 5. Honest framing for the PM conversation

A few things worth being precise about when discussing externally:

- **The "AGE benchmark is slow" narrative needs nuance.** AGE's *core
  graph engine* is slow on this workload relative to dedicated graph
  DBs, but the *PostgreSQL substrate* underneath it is doing fine.
  Most of our wins came from leaving AGE Cypher for outer SQL on
  denormalized side tables — which is essentially Postgres performance
  with AGE used as a thin compatibility layer. That is a defensible
  position for clients who value the Postgres stack, but it's not
  "fast Apache AGE Cypher."

- **Comparing throughput numbers across blog posts is unsafe.** The
  Neo4j and TigerGraph LDBC numbers in public benchmarks are on
  different hardware, different tuning, and (importantly) without the
  workarounds-as-correctness-trades we ship (MVCC drop log, IC13 /
  IC14 stubs). Any comparison table needs a footnote about the
  asymmetry, or we will get caught on it.

- **The 1:113 SF3:SF0.1 throughput ratio is real and it is bad**
  (`sf3-final-report.md:22`). It's driven by the IC long-tail
  (IC5 / IC10 / IC12). The schema denorm work has bent that curve,
  but the SF1000 projection for IC12 is still in the multi-minute
  range without further engine work.

- **We do not yet have a clean head-to-head SF1000 number on
  comparable hardware against Neo4j or TigerGraph.** Quoting one
  from memory would be guessing. The Horizon DB run plus the iter-3
  artifact is what we have right now. If the meeting demands a
  number, the truth is: "we project AGE at iter-3 + AGE 1.7 + Horizon
  hardware to land within a 2–10× factor of Neo4j on most queries
  and at parity on the ones we've fully denormalised, with IC12 and
  IC13 / IC14 as known outliers." We should not promise tighter than
  that without the measurement in hand.

## 6. Recommended next steps (if asked)

1. **AGE 1.7 upgrade** — single biggest correctness + concurrency win.
   Estimated 1–2 weeks (compatibility check, validate at SF0.1 + SF3,
   remove retry workaround, multi-thread stress at thread_count=8).
2. **SF10 / SF100 baseline on Horizon DB** — convert SF3 wins into
   real production-shape numbers. Coordinate with infra team for
   shared-infrastructure scheduling.
3. **Tier-1 denorms (HAS_CREATOR.creationDate, TagClass transitive
   closure)** — clears IC2 / IC8 / IC12 SF1000 risks. Pure
   engineering, no engine dependency.
4. **Quarterly re-review of "ceiling reached" queries** as AGE
   upstream advances. Several planner pathologies in §2.3 are
   plausible candidates for upstream fixes.
